腾讯IM ↔ 唐僧叨叨 互通中间层 需求说明
日期：2026-09-25
1. 背景与目标
建设一个独立的“桥接中间层”（下文称 Bridge），让腾讯 IM 体系和唐僧叨叨体系的用户在不改各自客户端代码的前提下互相收发消息。
现状：两套服务端都已存在并独立运行，但代码结构、通讯协议、数据模型完全不同，互相不认识对方的用户、群和消息。
目标：
消息互通：腾讯 IM 安卓端发出的消息，能到达唐僧叨叨安卓 / iOS 端；反向同样成立。
关系互通：好友关系、群组及群成员在两边保持一致。
资料互通：昵称、头像等用户资料两边可见。
媒体互通：图片、语音、视频、文件在对端能正常展示和播放。
对用户透明：用户感知不到对方在另一套系统里。
核心思路：不直接连两边数据库，而是在接口层打通——腾讯 IM 是云服务，数据库不对外开放；唐僧叨叨消息由悟空 IM 内核存储，直写库会绕过推送和同步逻辑。所以“数据打通”落地为：监听一边的回调 / Webhook，转换格式后调用另一边的服务端 API 写入。
2. 系统现状与消息链路
消息在两套系统之间只经过 Bridge 一个转换点，每个方向都是“源系统回调 → Bridge 转换 → 目标系统 API”。
表中唐僧叨叨侧的接口名和字段以开源版为准，需对照贵方实际部署的代码版本核实。
3. 功能需求
所有功能都建立在一张“ID 映射表”之上：同一个人、同一个群、同一条消息，在两边各有一个 ID，Bridge 必须能双向查到。
3.1 账号映射（F1）
腾讯侧用户首次与叨叨侧产生交互时，Bridge 在叨叨侧创建一个“影子账号”；反向同理，在腾讯侧调用账号导入接口创建影子账号。
映射表记录：腾讯 UserID ↔ 叨叨 UID、来源系统、创建时间。
影子账号不能登录，只作为消息的发送者 / 接收者存在。
需定义 ID 命名规则，避免两边 ID 冲突（如影子账号加前缀 tx_ / dd_）。
3.2 用户资料与头像（F2）
同步昵称、头像，可选性别、签名。
头像传 URL；若对端客户端访问不到该 URL（防盗链、内网地址），需转存到对端存储。
资料变更后 1 分钟内同步到对端。
3.3 好友关系（F3）
跨体系加好友：申请、同意、拒绝、删除在两边同步。
黑名单：一边拉黑后，另一边发来的消息应被 Bridge 拦截。
备注名为个人数据，不跨系统同步。
3.4 群组（F4）
映射群 ID：腾讯 GroupId ↔ 叨叨群 channel_id。
同步建群、解散、群名称 / 头像 / 公告修改、成员加入 / 退出 / 踢出、群主转让、管理员设置、禁言。
需确定“主群”在哪一边：建议谁创建谁是主，另一边是镜像。
腾讯群类型（Work / Public / Meeting / AVChatRoom）与叨叨群的对应关系需定义，默认只支持 Work / Public。
3.5 消息类型（F5）
唐僧叨叨 type 编号按开源版填写，开发前需对照实际代码核对。
3.6 媒体文件（F6）
跨系统的图片 / 语音 / 视频 / 文件，默认由 Bridge 下载后转存到对端存储，再把新 URL 写入消息。
语音格式：腾讯 SDK 默认录制格式与叨叨端可播放格式可能不同（如 AAC / M4A 与 AMR / OPUS），需确认两端播放器支持范围，不一致则用 ffmpeg 转码。
大文件（如 >100MB）可只传链接不转存，阈值待定。
3.7 会话与消息状态（F7）
撤回：一边撤回，另一边对应消息同步撤回（依赖消息 ID 映射）。
已读回执：单聊已读可同步；群已读作为二期需求。
离线推送：由各自系统原有推送负责，Bridge 写入消息时需带上推送标题 / 内容。
历史消息：只保证上线后的新消息互通；存量历史迁移不在本期范围。
不在范围：音视频通话、直播间、输入状态。
4. 非功能需求
最关键的两条是“不丢、不重”：任何消息要么成功到达对端，要么可查到失败记录；重试不能产生重复消息。
5. 边界、假设与待确认问题
以下假设决定了方案走向，开发前需逐条确认。
假设
“腾讯 IM 服务端”指腾讯云 IM（托管服务），我们可以配置其第三方回调地址并调用 REST API。
唐僧叨叨为自部署版本，有源码或至少有管理员 API 权限，可配置 Webhook。
两端客户端代码不改或少改，所有适配在 Bridge 完成。
一个真实用户只在一套系统有账号，另一边是影子账号。
待确认

☐ 腾讯 IM 套餐是否包含第三方回调？REST API 频率限制是多少？
☐ 唐僧叨叨的实际版本号，是否在开源版基础上改过消息结构？
☐ 腾讯安卓端用了哪些自定义消息（TIMCustomElem）？需要完整清单。
☐ 两端语音录制格式分别是什么？
☐ 预估用户数、日消息量、峰值 QPS。
☐ 是否需要迁移存量好友关系和群，还是只桥接上线后新建的？
☐ 数据合规：用户数据在两套系统之间流转是否需要用户协议或隐私政策调整？

事件出口 | 第三方回调（发消息后、加好友后、建群后等） | 悟空 IM Webhook + 业务服务事件
消息格式 | MsgBody 数组，元素如 TIMTextElem、TIMImageElem、TIMSoundElem | payload JSON，type 字段区分文本 / 图片 / 语音等
会话标识 | 单聊用 UserID，群聊用 GroupId | channel_id + channel_type（1 个人，2 群）
媒体存储 | 腾讯云 COS（SDK 上传） | 自建对象存储（MinIO / OSS 等）

类别 | 要求 | 建议指标
时延 | 文本消息跨系统额外延迟 | P95 < 500ms（不含媒体转存）
时延 | 含媒体消息 | P95 < 3s（图片 / 语音）

顺序 | 同一会话内消息有序 | 按会话 ID 分区串行处理
吞吐 | 峰值消息量 | 待确认；设计上支持水平扩容
安全 | 回调鉴权 | 校验腾讯回调签名、叨叨 Webhook 来源 IP / Token
安全 | 密钥管理 | 腾讯 SecretKey、叨叨管理 Token 不入代码库
限频 | 腾讯 REST API 有调用频率限制 | Bridge 内置令牌桶限流，超限排队
可观测 | 链路可追踪 | 每条消息记录源 ID、目标 ID、耗时、状态；失败率告警
容灾 | Bridge 宕机 | 回调先入队再处理，恢复后续传；腾讯回调超时不应影响其正常下发
