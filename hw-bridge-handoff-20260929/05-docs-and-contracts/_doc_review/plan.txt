0001 华为端（腾讯 IM）与唐僧叨叨互通：详细开发实施方案
0002 日期：2026-09-26
0003 1. 结论与实施总览
0004 按方案 A+（代理在线 + 拉取补偿）实施：中间层替每个华为用户在叨叨侧常驻一个“无头 PC 客户端”，实时收发；同时内置两条补偿通道（叨叨侧同步接口、腾讯侧漫游消息），保证不丢、不重、不回环。叨叨服务端与悟空 IM 的代码、配置零改动；改动只落在新建的中间层和腾讯一侧（腾讯侧后端 6 处、华为端 App 7 处）。
0005 本文统一用“角色名”指代各代码包，不用品牌名：华为端 App（腾讯 IM 安卓端）、腾讯侧后端（华为端 App 调用的 PHP 业务后端）、叨叨服务端（唐僧叨叨业务服务 + 悟空 IM）、叨叨安卓端。人名缩写：H = 华为用户，T = 叨叨用户，影子账号 = T 在腾讯 IM 里的对应账号。
0006 1.1 实施原则
0007 以叨叨为准：凡是涉及叨叨用户的好友、群、成员、群资料，叨叨是唯一数据源，腾讯侧只是镜像。
0008 在叨叨侧只以当事人身份操作：所有叨叨写操作都用当事华为用户自己的代理连接或 token 完成，不用管理员接口，叨叨的好友校验、群成员校验、租户限频、黑名单全部自动生效。
0009 在腾讯侧用独立管理员：中间层调用腾讯 REST 一律用新建的管理员账号 bridge_admin，回调里凡是它发起的操作都能识别出来并忽略。
0010 先落库、后回执：至少一次投递 + 幂等表 = 恰好一次的效果；任何一步失败都进重试队列，最终由定时对账兜底。
0011 可一键停用：停掉中间层，叨叨与悟空不受任何影响；华为端只是暂时收不到叨叨侧消息，恢复后自动追平。

0032 3.1 部署
0033 机器：2 台 Linux 虚机或 2 个容器，每台 4 核 / 8 GB / 100 GB SSD；内网直连 master:8090（叨叨业务服务）和 master:15200（悟空 WebSocket，master 的 Nginx 负载到 node1–3 的 5200）。
0034 主备：两个实例都开 HTTP 入口，腾讯侧后端打到哪个都行（入口只入队）。只有持有 Redis 租约 hwb:leader 的实例建代理连接、消费队列、跑定时任务。租约 TTL 15 s，每 5 s 续约；主实例挂掉后备实例在 20 s 内接管，并对全部用户执行重连追平。
0035 为什么不双活：悟空对同一 device_id 的从设备连接是“新连接关旧连接”（event_connect.go），两个实例同时连同一用户会互相顶掉。500 人规模单实例足够；将来到几千人再改“按 uid 分片 + 分片租约”。
0036 数据库：独立库 hw_bridge（MySQL 8）。可以放进叨叨现有 MySQL 集群（写入口 6446），但用独立账号、只授权本库；不得读写叨叨的业务库。Redis 用独立 DB 编号或独立实例，键前缀 hwb:。
0037 ffmpeg：镜像基于 Debian / Ubuntu，其 ffmpeg 包带 AMR-NB 编码器；镜像构建时执行 ffmpeg -hide_banner -encoders | grep amr_nb 校验。
0038 3.2 网络与端口
0039 3.3 容量估算
0040 连接：500 条 WebSocket，每条 30 s 一次心跳，约 17 次/s；内存 200 MB 以内。
0041 消息：按每人每天收发 200 条估算，500 人约 10 万条/天，峰值 20–50 条/s。同一条群消息会被群内 N 个华为成员的代理各收一次，按 message_id 去重后只处理一次。
0042 腾讯 REST：中间层默认限速 50 次/s，远低于套餐限频（以控制台显示为准）。
0043 叨叨同步接口：主备切换或悟空重启后 500 人同时追平，按并发 10 限流，避免冲击叨叨。

0050 4.4 并发与队列模型
0051 叨叨 → 腾讯：代理连接的读循环把消息按会话键（单聊 p:<小uid>:<大uid>，群 g:<group_no>）投入 keyed executor，同一会话串行、不同会话并行（默认 64 个 worker）。处理成功才 recvack，所以不需要额外队列：未回执的消息由悟空重投，连接断了由重连追平按游标补拉。
0052 腾讯 → 叨叨：回调先写 inbox_event（唯一键去重），主实例的 dispatcher 每 200 ms 轮询一次（同实例入队时立即唤醒），按会话键串行处理。
0053 其他任务（建镜像群、导影子账号、对账、资料刷新）进 job 表，带 next_run_at 和指数退避。
0054 毒消息：同一会话内连续失败 3 次（1 s / 3 s / 10 s）即转死信并告警，后续消息继续处理，不让一条坏消息卡住整个会话。

0062 5.3 字段约定
0063 单聊频道键：两个叨叨 uid 按字典序拼成 <小>:<大>，与叨叨 GetFakeChannelIDWith 的思路一致；单聊 message_seq 是频道级的，两人看到的 seq 相同。
0064 游标只前进：sync_cursor.last_seq 只在一条消息处理完成（成功、忽略或进死信）后前进，用 UPDATE ... SET last_seq = GREATEST(last_seq, ?)。
0065 加密：密钥 HWB_DATA_KEY（32 字节）只从环境变量或密钥文件读取；密文格式为 key_id(1 字节) || nonce(12) || ciphertext，换密钥时新写入用新 key_id，旧数据由后台任务重加密。解密后的 token 只放进程内存，不进 Redis、不进日志。
0066 清理：每天凌晨分批删除过期数据（每批 5000 行）；msg_map 如果单表超过 5000 万行改按月分区。

0086 6.7 token 续期与账号状态
0087 每日续期：凌晨任务对 token_login_at 超过 7 天的用户调 usernamelogin（flag=2）。正常情况下返回同一个 token，有效期重置为 30 天；如果返回新 token（缓存过期或被清），更新库并让该用户的代理连接立即重连。
0088 被动续期：叨叨接口返回 401，或悟空连接返回原因码 2（认证失败）时，立即重新登录一次再重试。
0089 被叨叨禁用：登录返回“该用户已被禁用”或连接返回原因码 19（封禁）→ status=2，停止代理，告警并通知腾讯侧后端（是否同步封禁腾讯账号由运营决定）。
0090 租户停用：登录被拒、发送返回原因码 25 → 告警，华为用户发消息时收到“暂时无法发送”提示。
0091 密码不外泄：叨叨密码只有中间层知道；如果有人用它登录叨叨 PC，会覆盖掉悟空里该用户的 PC token（悟空每个 uid + 设备类型只存一个 token），导致代理下次重连失败。华为用户改腾讯侧密码不影响叨叨密码。

0113 7.4 会话状态机
0114 Syncing 阶段实时收到的消息照常处理，补拉到的消息与实时消息都先查 msg_map，谁先到谁处理。
0115 7.5 心跳与重连
0116 每 30 s 发一次 ping；10 s 内没有收到任何帧就关闭连接重连。
0117 退避：1 s、2 s、4 s … 最长 60 s，加 ±20% 抖动。
0118 悟空节点重启或主备切换时，500 条连接在 30 s 内随机分散重连，追平任务并发限制为 10。
0119 失去租约时立即关闭全部连接（直接关 WebSocket），不再回执任何消息。
0120 7.6 发送与回执的实现要点
0121 每条连接一个读协程、一个写协程；请求带自增 id，用 id → channel 的表等待响应，超时 10 s。
0122 clientMsgNo = hwb_ + sha1(来源键) 的前 24 位十六进制。同一条腾讯消息重试多少次都是同一个号，既用来防回环，也用来重试前查重。
0123 收到 recv 后先判断是否需要转发，处理完成或决定忽略后才 recvack；指令消息、noPersist 消息同样要回执。
0124 未回执的消息悟空会在同一连接上重投（event_pushonline.go setupRetryIfNeeded），所以处理函数必须幂等。

0153 8.2 腾讯 → 叨叨
0154 处理步骤：
0155 入口：POST /cb/tim，body 是腾讯回调原文，请求头带 HMAC 签名和 X-TIM-Query（腾讯回调 URL 上的 SdkAppid、CallbackCommand、ClientIP、OptPlatform 等原始参数）。验签通过就按命令算 dedup_key 写 inbox_event，写成功或唯一键冲突都返回 200。
0156 过滤（标记忽略）：
0157 单聊：From_Account 不是华为用户，或 To_Account 不是影子账号 → 忽略（华为用户之间的聊天只在腾讯）。
0158 群：GroupId 不以 dd_ 开头，或 From_Account 不是华为用户 → 忽略。

0160 CloudCustomData 带 hwb 标记 → 忽略。

0200 语音转码
0201 腾讯 → 叨叨：ffmpeg -i in.m4a -ac 1 -ar 8000 -c:a libopencore_amrnb -b:a 12.2k out.amr；时长用 ffprobe。波形按叨叨安卓端 AudioRecordManager.getDbs() 的格式生成：每 100 ms 取峰值，算 20·log10(峰值)，每段一个字节（0 改成 2），整体 base64。波形可以省略，叨叨端没有波形也能播放。
0202 叨叨 → 腾讯：ffmpeg -i in.amr -ac 1 -ar 16000 -c:a aac -b:a 32k out.m4a，用 H 的 token 上传到叨叨存储（路径 /1/<对方uid>/...m4a）后把公开地址填入 TIMSoundElem.Url。华为端的 TUIKit AudioPlayer 用系统 MediaPlayer，安卓原生能解 AMR-NB；阶段 0 如果实测华为机能直接播 AMR，可省掉这一步。
0203 叨叨 iOS 录制格式待阶段 0 实测；转码前用 ffprobe 按实际格式处理，不凭扩展名判断。

0209 10. 好友关系同步：双向流程
0210 华为用户与叨叨用户之间的好友关系以叨叨为准：叨叨确认成为好友后，中间层才在腾讯侧强制添加双向好友。华为用户之间的好友只在腾讯，不同步。叨叨的好友申请必须带 vercode，申请 token 15 天过期（FriendApplyExpire），这两点决定了下面的流程。
0211 10.1 状态
0212 friend_link 状态：1 = H 已申请待 T 确认；2 = T 已申请待 H 确认；3 = 好友；4 = H 已删；5 = T 已删；6 = 拒绝或过期。
0213 10.2 叨叨用户加华为用户（T 发起）
0214 T 在叨叨按用户名搜到 H（H 在叨叨有用户名），发起 /v1/friend/apply。
0215 叨叨给 H 发指令 friendRequest（参数 apply_uid、apply_name、to_uid、remark、token），H 的代理收到；离线期间漏掉的由指令同步补回。
0216 中间层写 friend_link(H, T) = 2，记下 token 和过期时间；确保 T 的影子账号已导入（昵称、头像）；调腾讯 friend_add（From = T，To = H，AddType = Both，ForceAddFlags = 0，AddWording = 附言）。
0217 H 的加好友方式是“需要验证”（默认）：腾讯生成待处理申请，华为端“新的联系人”出现 T，用的是 TUIKit 原生界面。
0218 “允许任何人”：腾讯直接成为好友并触发添加回调，直接走第 4 步。
0219 “拒绝任何人”：腾讯返回失败，中间层调叨叨 PUT /v1/friend/refuse/<T> 拒绝，状态置 6。
0220 H 同意 → 腾讯 Sns.CallbackFriendAdd → 腾讯侧后端转发 → 中间层用 H 的 token 调叨叨 POST /v1/friend/sure {"token":"..."}，状态置 3。叨叨会建双向好友、加悟空白名单，并发两条消息：H → T 的提示“我们已经是好友了…”（发送人是华为用户，按防回环不转腾讯）、T → H 的申请附言（转到腾讯，华为端看到 T 的第一句话）。
0221 H 拒绝：腾讯没有对应回调。华为端 App 在拒绝影子账号申请时调 /api/bridge/friend_refuse（可选改造），中间层调 PUT /v1/friend/refuse/<T>；不改的话叨叨侧申请 15 天后自然过期。
0222 过期后才同意：叨叨 sure 返回“获取好友申请token的信息失败”，中间层改为替 H 向 T 发起申请（10.3），并给 H 发提示“对方的申请已过期，已替你向对方发送好友申请”。
0223 10.3 华为用户加叨叨用户（H 发起）
0224 找人：华为端“添加好友”页输入叨叨用户名 / 手机号 / 短号 → App 调 /api/bridge/search_user → 中间层调叨叨 GET /v1/user/search?keyword=（不需要登录），命中返回 {uid, name, vercode} → 中间层导入影子账号、把 vercode 存入 vercode_cache（source=search），返回 {user_id, nick, face_url}。App 打开 TUIKit 资料页（影子账号已导入，能读到资料）。叨叨搜索本身不按租户过滤，行为与叨叨客户端一致。
0225 申请：资料页“添加好友”→ 改造后的 ContactProvider.addFriend 发现对方是影子账号（32 位十六进制），改调 /api/bridge/friend_apply → 中间层按顺序找 vercode：搜索缓存 → 名片缓存 → 共同群（GET /v1/users/<T>?group_no=<共同群>，群允许加好友时才返回）→ 用 H 的 token 调 POST /v1/friend/apply {"to_uid":"<T>","remark":"<附言>","vercode":"..."}，状态置 1。App 提示“已发送好友申请，等待对方验证”。
0226 叨叨返回“已经是好友，不能再申请！”：直接在腾讯侧强制添加双向好友。
0227 拿不到 vercode 或叨叨返回“验证码不能为空”：提示“请通过搜索账号或名片添加”。
0228 T 同意：叨叨发指令 friendAccept（发给双方）→ H 的代理收到 → 中间层调腾讯 friend_add（From = H，To = T，Both，ForceAddFlags = 1），状态置 3。叨叨同时发的 T → H 提示转为 bridge_tip，H → T 的附言按防回环不转。
0229 T 拒绝：叨叨 refuse 只改申请状态，不通知申请人。状态停在 1，30 天后清理为 6。
0230 10.4 删除好友
0231 H 删 T：华为端删除好友 → 腾讯 Sns.CallbackFriendDelete → 中间层用 H 的 token 调 DELETE /v1/friends/<T>，状态置 4。叨叨的删除是“我删对方、对方变单向”，之后双方发消息都会被预校验拦下。
0232 T 删 H：叨叨只给 T 自己的设备发 friendDeleted，给 H 发的是 channelUpdate（channel_id = T）。H 的代理收到后，中间层调 GET /v1/friend/sync?version=<friend_version>&limit=200，发现 T 的记录出现 be_deleted = 1 或 is_deleted = 1，就调腾讯 friend_delete（Delete_Type_Both），状态置 5。
0233 兜底：每小时做一次好友对账（第 14 节）。
0234 10.5 黑名单
0235 H 拉黑 T：腾讯 Sns.CallbackBlackListAdd → 叨叨 POST /v1/user/blacklist/<T>；移出：Sns.CallbackBlackListDelete → DELETE /v1/user/blacklist/<T>。叨叨拉黑后悟空会拦下 T 发给 H 的消息。
0236 T 拉黑 H：叨叨不通知 H。H 再发消息会收到原因码 4，中间层发 bridge_tip“消息已发出，但被对方拒收”。不镜像到腾讯，因为 T 解除拉黑时叨叨同样不通知，镜像了反而没法撤销。

0266 12. 撤回、已读、未读、资料与头像
0267 撤回和单聊已读双向同步，定位全靠 msg_map；叨叨的“已读”和“管理员删除他人消息”都通过指令 syncMessageExtra + 拉消息扩展来传递，其中已读指令不存储，必须有对账兜底。
0268 12.1 撤回
0269 叨叨 → 腾讯
0270 消息扩展拉取：POST /v1/message/extra/sync {"channel_id","channel_type","extra_version","limit":100}，返回每条消息的 revoke、readed、readed_count、is_mutual_deleted、content_edit、extra_version。按“华为用户 + 频道”记录最大 extra_version（sync_cursor 增加 extra_version BIGINT 列）。
0271 腾讯 → 叨叨
0272 说明：叨叨的 revoke 必须传 client_msg_no（为空会报“撤回主键参数错误”），同时要传 message_id（更新消息扩展时用）。叨叨服务端没有撤回时限，TUIKit 默认 2 分钟内可撤回。叨叨拒绝时只记日志（腾讯侧已撤回，极少出现）。
0273 12.2 已读
0274 T 读了 H 的消息（叨叨 → 腾讯）：叨叨只对 setting.receipt = 1 的消息记已读。中间层代 H 发单聊时按对方的回执设置带上 setting.receipt。叨叨每 3 秒汇总一次已读，给发送者发不存储的指令 syncMessageExtra（message/event.go）。H 的代理收到后拉消息扩展，对 readed 或 readed_count 变为大于 0 的消息，在腾讯调 admin_set_msg_read {Report_Account: T, Peer_Account: H}，华为端单聊显示“已读”（前提是华为端 App 开启了 TUIKit 的单聊已读回执展示，阶段 0 验证该接口是否会触发对端的已读状态更新）。
0275 H 读了 T 的消息（腾讯 → 叨叨）：腾讯 C2C.CallbackAfterMsgReport（Report_Account = H、Peer_Account = T、LastReadTime）→ 从 msg_map 找 T 发给 H、时间 ≤ LastReadTime、need_receipt = 1 且还没同步的消息 → 用 H 的 token 调 POST /v1/message/readed {"channel_id":"<T>","channel_type":1,"message_ids":[...]}，read_synced 置 1。
0276 指令丢失兜底：已读指令不存储，代理断线期间会丢。每 10 分钟对“24 小时内有 H 发出消息且仍有未读”的单聊拉一次消息扩展。
0277 群已读：本期不做。
0278 12.3 未读
0279 H 在腾讯读完单聊后，除了上报已读，还用 H 的 token 调 PUT /v1/coversation/clearUnread {"channel_id":"<T>","channel_type":1,"unread":0}（路径拼写就是 coversation），清掉 H 在叨叨侧的未读。

0385 18.2 方案 F：纯拉取
0386 思路：不建常驻连接，调度器定时替每个华为用户调叨叨同步接口；发送时临时建连接。
0387 轮询节奏（自适应）
0388 全局限速 50 次/s，超出时按热度优先。500 人按平均 15 s 一次估算，约 33 次/s 会话同步，再加上有变化频道的补拉。
0389 每次轮询
0390 POST /v1/conversation/sync（带 version 和 last_msg_seqs，只返回有变化的会话）。
0391 有变化的频道按游标 POST /v1/message/channel/sync。
0392 每 5 次轮询做一次指令同步 POST /v1/message/sync + syncack。
0393 已读类指令不存储，拉不到，靠定时 extra/sync（12.2）。
0394 华为 → 叨叨：收到腾讯回调后为该用户建临时 JSON-RPC 连接（connect → send → 等回执），空闲 60 s 后关闭，连续发送复用同一条。发送仍走叨叨预校验。
0395 代价：延迟等于轮询周期；正在输入、在线状态做不了；对叨叨业务服务的请求量比 A+ 高。
0396 什么时候用：悟空 WebSocket 入口不可用或限制连接数时；或作为 A+ 故障期间的降级模式。A+ 已经实现了同步客户端、游标和临时发送连接，把配置 mode 从 realtime 改成 polling 即可切换。
0397 18.3 方案 D：悟空插件
0398 组件：一个 Go 写的悟空插件 hwbridge.wkp（用悟空官方 Go 插件 SDK），声明 Receive 方法。插件可声明 ReplySync 让悟空同步调用（超时 plugin.timeout，默认 1 s），默认异步。
0399 部署：放到 3 个悟空节点的 <rootDir>/plugins/ 目录。悟空用 fsnotify 监听该目录，发现 .wkp 文件就以 ./hwbridge.wkp --socket <socket> --sandbox <dir> 启动（internal/plugin/server.go），不一定要重启。但容器部署时插件目录要挂卷或改镜像，仍是生产部署变更；离线推送在消息分发所在节点执行，所以 3 个节点都要装。
0400 绑定：每注册一个华为用户，调悟空管理接口 POST /plugin/bind {"plugin_no":"<插件编号>","uid":"<华为用户叨叨 uid>"}，需要悟空管理 token。
0401 什么时候触发（internal/pusher/handler/event_pushoffline.go）：接收者是绑定用户且主设备离线（华为用户没有叨叨 APP 设备，始终算离线）、发送者不是自己、不是只同步一次的指令、发送者不是系统账号。
0402 插件拿到什么：RecvPacket{FromUid, ToUid, ChannelId, ChannelType, Payload}（internal/types/pluginproto/plugin.pb.go），没有 message_id、message_seq、client_msg_no、时间戳。
0403 插件做什么：把 RecvPacket 连同一个签名 POST 给中间层 /cb/wk_plugin（地址用 /pluginconfig/:plugin 下发）。
0404 华为 → 叨叨：插件 RPC 发送按系统设备处理，跳过好友预校验、租户限频和黑名单，不能用；只能仍用临时连接。
0405 为什么单独用不行：收不到指令（好友申请、撤回、成员变化、已读）；收不到系统账号发的群提示；群消息 N 份无法去重；撤回无法定位；失败不重试。
0406 18.4 方案 D+F：插件当门铃，拉取补全
0407 插件 Receive 到达中间层后，只用它的 (ToUid, ChannelId, ChannelType)：立即对该用户该频道按游标执行一次 channel/sync，拿到带 ID 的完整消息后走第 8 节流程。同一频道 500 ms 内的多次门铃合并成一次拉取。
0408 指令、群提示、已读仍靠 F 的定时拉取（周期可放宽到 30 s）。
0409 发送用临时连接。
0410 优点：不需要 500 条常驻连接，消息接近实时。
0411 缺点：生产悟空部署变更、要持有悟空管理 token、插件要随悟空版本维护（3 个节点版本一致、崩溃重启），与“叨叨以稳定为主”冲突。
0412 什么时候考虑：将来悟空本身要升级或重构部署时，在那次变更里一起评估。
0413 18.5 方案 A（没有补偿的代理在线）
0414 只有常驻连接、不做追平和对账。悟空的未回执重投只在同一条连接上有效，连接断开期间的消息会丢，所以只作为阶段 3 之前的开发中间态，不上生产。
