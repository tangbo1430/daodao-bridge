# 华为企才汇与唐僧叨叨剩余业务功能实施计划

日期：2026-09-29

## 范围和基线

- Android 使用 `02-authoritative-qch-source/企才汇源码交付-20260810/Android/qch` 及同级 `Android/TUIKit`。
- PHP 以 `02-authoritative-qch-source/企才汇源码交付-20260810/PHP-Web/qicaihui.com` 为原始源码，Bridge 改造从 `03-php-deployment/backend` 延续。
- Bridge 使用 `01-bridge/tencent-tangseng-bridge`，独立部署于 `101.32.11.27:/opt/hw-bridge`；PHP 保持 `23.251.34.150:/root/IM/YCH-IM-deploy` 的 Docker 部署。
- 现有腾讯 IM ↔ 叨叨 PC(2) 文本单聊、基础幂等、防回环、重试和单实例运行方式保留。叨叨业务服务端、悟空 IM 核心和 APK 到叨叨的直连均不在改动范围。
- 本阶段不实施主备、Leader、Redis 租约、死信专项、压测或 72 小时稳定性优化。所有业务功能验收后，再另行安排可靠性工作。
- 真实凭据只从服务器现有 `.env` 或安全环境变量读取；源码、APK 和发布包均不得包含生产密钥或硬编码测试账号。

## 共同实施门槛

每类功能按同一顺序交付：确认文档和现有代码入口 → 保存脱敏真实报文与契约样本 → 修改 Bridge、PHP、Android → 运行相应测试 → 构建发布包或 APK → 现网双向验证 → 记录结果与未验证项。协议与文档不一致时，以真实报文建立契约测试后调整客户端和 Bridge，不修改叨叨服务端。

Bridge 基础命令为 `go test ./...`、`go vet ./...`；PHP 对改动文件执行 `php -l` 和对应接口测试；Android 执行相关模块编译及 `assemble`，再用真机验证。每阶段发布前核对补丁包内文件与工作源码的 SHA256。部署先备份、再使用 `06-release-and-deploy` 中的脱敏脚本，并保留服务器 `.env`。

## 阶段 1：好友关系完整闭环

### 1.1 现状

- Bridge 已有搜索、H→T 申请和 T 同意后的基础 `friendAccept` 处理；`friend_refuse` 目前返回 501。
- 腾讯 `Sns.CallbackFriendAdd/Delete/BlackListAdd/BlackListDelete` 会由 PHP 转发，但 Bridge 目前仅存入 Inbox，尚未执行关系操作。
- PHP 已有搜索/申请的 Bridge 门面；拒绝、删除与黑名单缺少对应 Bridge 路由及服务方法。Android 已拦截影子账号搜索与申请，原生同意/拒绝和删除入口尚需接入桥接结果。

### 1.2 实施任务

1. 从叨叨 PC(2) 指令和腾讯 4 类关系回调保存脱敏样本，确认 `friendRequest`、`friendAccept`、`channelUpdate`、申请 token、操作者与目标 UID 字段。
2. Bridge 增加好友请求状态、申请 token/vercode 的持久化；T→H 申请用腾讯影子账号生成待确认申请；H 同意后以 H 的叨叨 token 执行 `friend/sure`，拒绝执行 `friend/refuse`。
3. H→T 申请沿用已有入口；T 同意后才执行腾讯双向好友镜像。补 H/T 删除、H 拉黑/解除，以及 T 删除后的叨叨好友状态同步。所有操作只使用 H 本人 token，普通腾讯好友不进入 Bridge。
4. 补影子账号 `portrait_set`、昵称和头像刷新；PHP 原好友问候语在任一方为影子账号时不发送。
5. PHP 增加经过 `login_token` 鉴权的拒绝、删除及必要状态接口；Android 在影子申请同意/拒绝与联系人删除入口调用对应 PHP 接口，普通联系人仍走原腾讯流程。

### 1.3 验收

H→T 和 T→H 的搜索、申请、同意、拒绝、删除、拉黑/解除拉黑及头像昵称变化逐项双端验证；无重复问候语，普通腾讯好友行为无变化。输出 Bridge/PHP 发布包和 Android 联调 APK。

## 阶段 2：群功能

1. 固定叨叨群创建、邀请、成员退出/踢除、解散、资料变更和群消息的真实样本及回调字段。
2. Bridge 建立 `group_map` 与 `group_member_mirror`，以叨叨 `group_no` 创建 `dd_<group_no>` 腾讯镜像群；群资料和成员以叨叨为准。实现成员增删、退群、解散与资料刷新。
3. H 发起的建群和邀请先经 Android→PHP→Bridge，以 H token 在叨叨成功后再更新腾讯镜像。T 发起的变化经代理指令同步至腾讯。群操作失败时把明确错误返回 APK。
4. 复用现有 Inbox/Outbox 处理双向群文本；确认 `Group.CallbackAfterSendMsg` 和多 H 代理同一消息的去重键，过滤 H 自身回声。
5. 增加 Android 的 `dd_` 群入口、邀请和退群交互；普通腾讯群保持原有路径。

验收：T 建群拉 H、H 建混合群和拉 T、成员增删、退出、解散、改资料及双向群文本均通过；腾讯镜像 ID 为 `dd_<group_no>`。输出对应发布包与 APK。

## 阶段 3：媒体和资料

1. 固定腾讯 `TIMImageElem/TIMFileElem/TIMSoundElem/TIMVideoFileElem` 和叨叨 type 2/3/4/5/8 的真实样本、文件上传响应及公网可访问 URL。
2. Bridge 实现受大小与超时限制的下载、临时缓存、以 H token 上传叨叨、相对路径与公网 URL 转换；图片/GIF、文件、语音和视频分别保留类型与元数据。语音编码先按实测格式决定是否用 ffmpeg 转码。
3. 同步 H/T 昵称和头像；不支持或超限内容生成明确的 `bridge_tip` 或文字链接，避免空白消息。
4. PHP 接通资料变更通知；Android 检查媒体发送与展示、失败提示及影子会话的资源加载。

验收：图片、GIF、文件、语音、视频分别双向真机收发；头像昵称更新可见；失败有可读提示。输出发布包和 APK。

## 阶段 4：撤回和已读

1. 固定两侧单聊/群撤回与已读事件的真实样本，确认腾讯 MsgKey/MsgSeq 和叨叨 message_id/seq 的映射。
2. Bridge 处理 T→H 和 H→T 的单聊/群撤回、单聊已读及叨叨侧未读清零；缺失原消息映射时记录可定位的业务失败，不伪报成功。
3. PHP 转发相关腾讯回调及管理员代撤回的实际操作人；Android 对影子会话展示撤回、已读和提示，不改变普通腾讯会话。

验收：两方向撤回、单聊已读和未读数在双端按方案变化。输出发布包和 APK。

## 阶段 5：账号和会话能力

1. 将 PHP 的资料修改、注销动作通知 Bridge；Bridge 用已有账号映射更新叨叨资料、停用影子账号并同步状态。
2. 按真实接口完成叨叨会话、频道、指令同步和腾讯漫游补偿，游标持久化，并将补得的消息送入现有消息处理路径。
3. 验证重新登录、Bridge 重启后的账号和会话恢复；本阶段只覆盖业务功能，不扩展为稳定性或高可用专项。

验收：资料、注销和影子状态一致；离线后重新上线可看到会话与消息。输出发布包。

## 阶段 6：APK 交互收尾与业务总验收

- 回归影子联系人、叨叨用户搜索、好友申请提示、群邀请、`bridge_tip`、影子会话隐藏不支持通话入口；普通腾讯联系人、单聊、群聊和媒体保持原样。
- 构建最终联调 APK，按实施方案 A–E 业务用例逐项记录设备、账号角色、操作、双方结果和脱敏日志；未通过的项目回到对应阶段修复。
- 业务总验收通过后，才开始另行安排死信、丢消息、重试策略、会话串行、主备、Leader、压测及长时间稳定性任务。

## 当前外部依赖

当前执行环境的 SSH 公钥已交给负责人，两台 CVM 尚未接受该公钥。代码与本地测试可先推进；现网 `.env` 核验、部署和真实端到端测试待 SSH 授权后执行。腾讯控制台回调开关、真实关系/群/媒体样本或接口参数若与交接文档不符，先记录差异和脱敏样本再处理。
